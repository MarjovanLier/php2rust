# Test PHP and its Rust output with one differential harness, from fixtures written once

Beside the folder tests of ADR 0004, php2rust gets a differential harness: each fixture is one JSON file that states a call or a run and what it must give (a golden fixture keeps what it must give in recorded files, see "Golden files"), and the same fixture runs on PHP and on the Rust that php2rust writes, under every supported PHP version (ADR 0009). PHP is the oracle: the harness first checks the fixture's expectation against PHP, then the Rust output against the same expectation, so a wrong fixture and a wrong conversion fail with different messages.

The harness does not keep a test runner in each language. From the fixture it writes one driver in PHP, a function `php2rust_fixture()` that calls the entry point with the fixture's arguments and prints each result. `echo` alone prints `1`, `1.0`, `"1"` and `true` alike, so the driver passes each result through a typed print helper of its own (`print_int(int $v)`, `print_string(string $v)` and so on) that writes the type before the value. A result of the wrong type then fails in PHP with a `TypeError`, because the driver declares `strict_types`, and does not compile in Rust; the one exception is the `int` that PHP's strict mode lets into a `float` parameter. PHP runs the subject with the driver. php2rust converts the subject and the driver together as a directory (P2R-170), which gives a library crate with no top-level statements (P2R-175), and the Rust runner builds that library crate with a one-line `main` that calls the converted `php2rust_fixture()`, then runs it. So the test itself is written once, in PHP, and converts like any other input; a fixture whose driver does not convert stops, as ADR 0001 requires, and that stop is the result. A probe on 28 Nov 2026 put a one-function subject and such a driver through `php2rust <dir> -o <out>` and built the crate with a one-line `main`; the Rust printed what PHP printed. The probe used plain `echo`, not the typed helpers.

An `e2e` fixture has no driver: its subject is a program with top-level statements, which converts as a single input with `fn main()` (P2R-72). The harness runs PHP and the built Rust program as processes in a temporary directory that holds the fixture's starting files, with the fixture's stdin and arguments.

There are four tiers, one directory each under `tests/differential/`:

- `unit/`: one function of a subject, called with the arguments of each case; its return value and its output are compared.
- `feature/`: one file or area of a subject (for example formatting or escaping), several entry points over one set of cases.
- `golden/`: like `feature/`, but the cases list inputs only, and what PHP gave for each input is recorded once in a golden file (see "Golden files").
- `e2e/`: a whole program run as a process, with its stdin, arguments and starting files; its stdout, exit code and the files it writes are compared.

A fixture is `<tier>/<id>-<slug>.json`, where `<id>` is the requirement it exercises, as for folders (`unit/p2r-46-echo-scalars.json`). It names its subject: a hand-written PHP file or directory under `tests/differential/subjects/`, or a path in the WordPress corpus (ADR 0011), which runs only when the corpus is present. A subject directory may hold `migrations/`, which the PHP side runs and php2rust reads with `--migrations` (P2R-400). A case gives its name, its arguments as JSON values (an integer and a float stay distinct), and for `e2e` its stdin, arguments and files, and, except in `golden/`, the expected stdout, return value, exit code and files written. A fixture may list `php` versions when it applies to fewer than all. Unit, feature and e2e expectations are written by hand.

## Golden files (amended 28 Nov 2026)

A function with many inputs, or an output too long to write by hand, gets a golden fixture. The harness has a record mode, turned on by `PHP2RUST_RECORD=1` and narrowed by `PHP2RUST_FIXTURE`, that runs only the PHP side of each golden fixture and writes one golden file per case, `golden/<id>-<slug>/<case>.txt`, holding the driver's typed output. Record mode runs on a developer's machine, never in CI. A recorded file is a claim about PHP that nobody wrote, so it is read in the diff and reviewed by hand before it is committed, as the testing method in the global wiki (`pages/dev/php-to-rust-port-testing.md`) describes. `PHP2RUST_BLESS=1` never writes or rewrites a golden file, and a normal run fails when a golden case has no file, so nothing is recorded by accident.

A normal run compares the PHP output and the Rust output of each golden case with its file, under every PHP version the fixture applies to. A file recorded under one version and failing under another is a difference between versions, which ADR 0009 treats as a finding, never as a reason to record again.

An output that changes from run to run (a time, a random number, an id the database chooses, the order of rows from a query without `orderBy`) would make a golden file wrong on the next run. Such a value is fixed where the fixture can give it to both sides (pass the time or the seed as an argument), and masked otherwise: the fixture lists masks, each a pattern and the text that replaces it, which the harness applies to the PHP output, the Rust output and the recorded file alike.

Record mode also runs PHP with code coverage and prints each line of the subject that no case reached, so the author sees which inputs are missing before the files are committed. PHP runs with `-n` as for the folders, which loads no Xdebug, so record mode names it by path: `-d zend_extension=<dir>/xdebug.so -d xdebug.mode=coverage`, where `<dir>` is the `extension_dir` that the PHP binary reports with its own configuration (on this machine `/opt/homebrew/lib/php/pecl/20250925`, checked with Xdebug 3.5.0 and PHP 8.5). Without Xdebug, record mode says so and records anyway.

## The PHP side of a Laravel subject (amended 28 Nov 2026)

The folder tests run Laravel code against stand-ins (`include/Eloquent.php`, `include/Data.php`): 78 such files under `tests/`, in 38 different versions of the Eloquent stand-in and 17 of the Data one, each holding only the parts its test names over rows kept in memory. A stand-in checks the test against the stand-in, not against Laravel. So the PHP side of a harness subject that uses Laravel runs the real packages: `laravel/framework` and `spatie/laravel-data`, pinned by a `composer.json` and `composer.lock` committed in `tests/differential/laravel/`, with `config.platform.php` set to 8.3.0, the lowest target of ADR 0009, so that Composer picks no version that needs a newer PHP. The packages are installed with `composer install` into `tests/differential/laravel/vendor/`, which `.gitignore` lists and which is never committed. Before the subject, PHP runs a bootstrap from that directory, given with `auto_prepend_file` as the folders give `prepend.php`: it boots Eloquent on an in-memory SQLite database, sets the facade root that `Schema::create` needs, and runs the subject's migrations in the order Laravel uses. The bootstrap is PHP only; php2rust never converts it, and reads the same migrations with `--migrations`. The stand-ins stay in the folder tests (ADR 0004); the harness does not use them.

Facts this rests on, checked on 28 Nov 2026 with Composer 2.10.3:

- With the platform set to PHP 8.3.0, Composer resolves `laravel/framework` v13.44.1 (which requires `^8.3`) and `spatie/laravel-data` 4.23.1, 83 packages and 43 MB in all. Without the platform setting it picks `symfony/console` v8.1.12, which requires PHP 8.4.1, so the setting is needed for 8.3.
- No locked package excludes PHP 8.6 by its constraint except `dragonmantank/cron-expression` v3.6.1 (`^8.2|^8.3|^8.4|^8.5`), its newest release, which `laravel/framework` requires and only its scheduler (`Illuminate/Console/Scheduling`) uses. The platform setting fixes the PHP that Composer resolves for, so `composer install` does not refuse that package under 8.6; whether 8.6 runs it is untested, and no harness subject uses the scheduler.
- 77 of the 83 packages are MIT; the others are BSD-3-Clause, Apache-2.0, or `nette/schema` and `nette/utils`, which offer BSD-3-Clause beside GPL. No package file enters the repository, only the two Composer files.
- `composer install` from the lock took 3.6 s with an empty Composer cache and 1.7 s with a full one. The README of `shivammathur/setup-php`, which CI uses, says it sets up the latest stable Composer by default and lists PHP 8.6 as stable.
- Homebrew's PHP 8.3.37, 8.4.28 and 8.5.13 with `-n`, as the folders run it, load `pdo_sqlite`, `mbstring`, `ctype`, `tokenizer` and `openssl`, and the real packages ran `create`, `findOrFail` with `ModelNotFoundException`'s message, `all()` and a Data class with an `Optional` property the same under all three. PHP 8.6 is not installed here.
- A probe ran the 25 case folders that use a stand-in and have a `main` on the real packages instead, through such a bootstrap and the folder's own migrations, under PHP 8.5; in each run no file under `include/` was loaded and `Model` came from `vendor/`. 23 printed the same stdout as with the stand-in. In `p2r-421-uncaught-find-or-fail` only the file and line of the uncaught exception differ, because they name the stand-in. `p2r-460-observed-models` stops, because its observer classes are declared in the stand-in.

Not checked: Laravel under PHP 8.6; which extensions PHP from `setup-php` on Ubuntu loads with `-n`, where they may be shared modules that only a configuration file loads; and how long a full harness run takes with Laravel booted once per case.

Decided by the owner on 28 Nov 2026: CI runs `composer install` and so fetches the Laravel packages from Packagist on every run (P2R-608). ADR 0011 rejected Composer for WordPress, because there it would add a package manager for one download of code that must stay out of the repository anyway; for Laravel, Composer is how the packages are published, and the lock file pins them.

## Considered Options

- A runner in each language that reads the JSON (a PHP script, and Rust code with `serde_json` that builds each converted function's arguments): rejected, because the Rust side would have to map JSON onto every converted signature, and two runners that must agree drift as two copies do (ADRs 0007 and 0008).
- Run WordPress's own PHPUnit tests through php2rust: rejected, because PHPUnit, its mocks and the test case classes are far outside what php2rust converts, and that code is GPL (ADR 0011). Its inputs can still be read when a fixture is written.
- More case folders only: rejected, because a case folder pins one program and its byte-exact Rust, and a function needs many inputs; writing one folder per input does not scale to WordPress.
- Expected values recorded from PHP by a command, as `PHP2RUST_BLESS=1` does for folders: rejected for unit, feature and e2e fixtures, because a recorded value that nobody reviews checks nothing; their expectations are written by hand and checked against PHP on every run. Amended on 28 Nov 2026: the golden tier records them, because hand-written expectations do not scale to many inputs, and its own command and review rule keep a recorded file from passing unread.
- Record golden files in CI, or let a normal run record a missing file: rejected, because a file written where nobody reads it is the unreviewed value the previous option rejects.
- Run Laravel subjects on the folder tests' stand-ins: rejected, because a stand-in has only what one test names, and a fixture that passes on it says nothing about Laravel.
- Commit `vendor/`, or Laravel's application skeleton with `orchestra/testbench`: rejected. `vendor/` is 43 MB of code that the lock file already pins, and an application or Testbench boots routes, config and service providers that Eloquent on SQLite and laravel-data's constructors do not need. A subject that needs more of Laravel adds it to the bootstrap.

Implemented on 28 Nov 2026 by section 53 of the spec (P2R-600 to P2R-609). Found while implementing it:

- With the real `vendor/` given as `--include` in place of the stand-ins, php2rust converted `p2r-350-data-struct`, `p2r-360-optional`, `p2r-410-model-store`, `p2r-412-find-forms` and `p2r-441-collection-store` to the same bytes as their `expected.rs`.
- A Laravel subject and its driver, converted as one crate and built with a one-line `main`, printed what PHP printed on real Eloquent, under Homebrew's PHP 8.3, 8.4, 8.5 and 8.6. The committed lock holds 84 packages; the probe above, with caret constraints, held 83.
- The first subjects stopped on four forms that php2rust does not convert yet, so they were rewritten in forms it does: a function and a local variable with one Rust name (P2R-31), a `?:` whose arms are a value and an `Optional` (P2R-180), a `?int` used in the `else` of a null check (P2R-106), and the value of an `Optional` after an `instanceof` check (P2R-34). Each is a slice for later, not a difference between PHP and Rust. The harness's own subject met two more: a `?:` that gives a string or `null`, and any float turned into text (`echo`, a join or `(string)`, P2R-166), so the driver has no `float` helper and a float result is out of reach until php2rust converts one; a float argument converts.
- Xdebug names a file by its real path, so on macOS, where `/var` links to `/private/var`, the coverage of record mode compares real paths.
- php2rust converts no read of stdin, no `$argv` and no file write yet, so the e2e seeds compare stdout and the exit code; the fields for stdin, arguments and files are there for when those convert.

## Consequences

- A fixture runs on Rust only when its whole subject converts, because php2rust writes nothing for a file with one stop (ADR 0001). A `unit` fixture on a WordPress file gives a Rust result only once that whole file converts; until then it runs on PHP alone, which still checks the fixture.
- The folder tests stay the contract for what php2rust writes; a fixture never replaces a case or stop folder for a form (ADR 0004).
- A fixture can test only what the driver's typed print helpers can show. Objects, resources and binary strings (JSON holds UTF-8 only) are out of reach until the form grows.
- Global state and starting globals need the converted driver to set them, which php2rust does not convert today, so a fixture that needs them stops until it does.
- The harness runs PHP once and rustc once per fixture and version; it needs PHP, rustc and rustfmt as the folders do, and `PHP2RUST_FIXTURE=<text>` keeps only the fixtures whose name holds the text, as `PHP2RUST_FOLDER` does.
- How the driver prints a map with keys that Rust orders differently, and whether a case may expect a stop instead of a result, are open questions for the change that implements this.
- A Laravel fixture needs Composer and network access to Packagist once per machine. When `tests/differential/laravel/vendor/` is missing, the runner skips the Laravel fixtures and prints one line that names `composer install`, as a corpus fixture is skipped without the corpus (ADR 0011); CI installs them (P2R-608).
- A Laravel upgrade is a change of the lock file, made on purpose and reviewed like the Mago pin (ADR 0002); a golden file that changes with it is reviewed again.
## Spec changes for the change that implements this

New requirements for the fixture format, the driver, the tiers, golden files and record mode, masks, the Laravel bootstrap and the runner, next to P2R-70 to P2R-76; P2R-75 (whether a fixture counts as cover for a requirement ID); P2R-76 (the rewrite command does not touch fixtures or golden files); P2R-77 and P2R-608 (CI installs the Laravel packages and runs the harness); P2R-82 (the README names the harness, its filter, record mode and `composer install`).
